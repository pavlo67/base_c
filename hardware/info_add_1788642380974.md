# GPIO abstraction and automatic software tests

This supplements hardware/info.md and replaces its previous description of desktop GPIO as no-op functions. RPI5 previously used those same no-op functions; it now uses lgpio.

## API

`Gpio` is an abstract, non-copyable class with shared validation and per-pin state. Public methods return 0 on success and a negative error code on failure, except `read()`, which returns 0 or 1 on success. Native library error codes are passed through; abstraction errors are named constants in gpio.h, starting at -10000. No exceptions are used for normal GPIO errors. Callers must serialize access; lifecycle is shared and is not reference-counted.

- `initialize()` opens the platform backend. Repeated calls preserve state.
- `terminate()` stops enabled PWM outputs, closes the backend, and resets state after successful close. Repeated calls are allowed. Concrete backend destruction also attempts cleanup.
- `setMode(pin, GpioMode::input/output)` configures a pin. Initial output configuration drives LOW. Repeating the current mode preserves the level. Changing mode stops PWM first. A failed reconfiguration leaves the pin unconfigured until a successful retry.
- `read(pin)` returns the backend's digital reading. `write(pin, level)` accepts only 0 and 1 and requires OUTPUT. Pins must be configured before use. Digital writes while PWM is enabled return PWM_ACTIVE; disable PWM first.
- `setRange(pin, range)` sets the integer duty scale, 1..40000. `setDuty(pin, duty)` accepts 0..range. Changing range preserves the numeric duty and rejects a range below that duty; it does not preserve the duty percentage.
- `setFrequency(pin, frequency)` sets the requested integer frequency, 1..10000 Hz. Hardware can quantize both frequency and duty; the API does not promise exact timing.
- `setEnabled(pin, enabled)` starts PWM or stops it and drives LOW. OFF retains range, duty, and requested frequency; repeated OFF also drives LOW. Zero duty is constant LOW and duty equal to range is constant HIGH while logically enabled.
- `getPwmSettings(pin, settings)` returns the last accepted settings, not measurements of the physical waveform. Defaults are range=100, duty=0, frequency=1000 Hz, enabled=false.

PWM operations require OUTPUT mode. Settings changed while disabled do not generate a signal. Enabled settings are applied through the backend before saving them. Invalid arguments do not change state; native operations involving several calls are not transactional on backend failure.

The supported public pin numbers are BCM GPIO0..27, not physical header positions. The programmer is responsible for choosing pins free for the intended use.

## Implementations and build selection

`hardware_gpio` links one implementation, selected by `BASE_GPIO_PLATFORM` in base/CMakeLists.txt:

- AUTO (default): native ARM builds read /proc/device-tree/model to distinguish Raspberry Pi 4 and Raspberry Pi 5; non-ARM builds use DESKTOP. Cross-compiling ARM or an unrecognized ARM board requires explicit selection.
- RPI4: requires pigpio headers/library. PWM uses gpioPWM with a native scale of 40000, converting the public duty ratio to that scale. pigpio selects its nearest supported frequency.
- RPI5: requires lgpio headers/library and access to /dev/gpiochip*. The RP1 controller is located by its pinctrl-rp1 label, rather than a hardcoded gpiochip number. Lines are claimed and released through lgpio. PWM uses lgTxPwm with duty converted to a percentage; it is software timed. Changes to active PWM can take effect at a cycle boundary. Constant LOW/HIGH endpoints stop any running PWM before a digital write.
- DESKTOP: an in-memory stub. Writes are readable, pins have independent state, and lifecycle/mode/PWM validation matches the real backends. It does not simulate external inputs or PWM edges: enabled 100% duty reads HIGH; other PWM duty settings read LOW.

The legacy SYSTEM_IS_RPI4/RPI5/DESKTOP build definitions remain available. CMake fails if the chosen platform library is missing rather than silently substituting a stub. Select BASE_GPIO_PLATFORM explicitly for cross-compilation; normal native builds select it automatically.

## Tests and probe

`gpio/_defines.h` contains GPIO_TEST_PINS (at least two distinct BCM pins, initially 17 and 24), GPIO_PROBE_PWM_PIN, and PWM probe constants. This particular _defines.h is included in version control so a fresh checkout builds without creating configuration files.

`gpio_test` uses the selected platform backend. It requires no jumpers, meters, or manual checks. It configures each selected pin as OUTPUT, reads X, writes 1-X, reads and compares, then writes X and checks again. Cleanup attempts to restore X even after an assertion failure. X is read after OUTPUT configuration, which initializes LOW; this does not restore the pin's mode or state from before the test started. On a Raspberry Pi it automatically drives the configured pins. Initialization/permission/claim errors fail the test; they are not silently skipped. CTest runs this test serially.

`gpio_contract_test` always links the desktop implementation, including on Raspberry Pi, and never accesses hardware. It checks independent pin states, invalid arguments, mode and lifecycle errors, PWM endpoints, OFF/ON settings retention, and configuration while disabled. These tests do not verify physical PWM frequency or duty.

Build and run from the repository root:

```sh
cmake -S base -B base/cmake-build-release
cmake --build base/cmake-build-release --target gpio_test gpio_contract_test gpio_probe stepper_motor_test
ctest --test-dir base/cmake-build-release -R '^(gpio_test|gpio_contract_test|stepper_motor_test)$' --output-on-failure
```

`gpio_probe` performs the same digital inversion check, reports its results, then runs PWM on GPIO_PROBE_PWM_PIN for GPIO_PROBE_PWM_DURATION_MS and turns it off. All configuration is in _defines.h; it takes no CLI parameters. Errors include a function prefix and numeric error code. PWM output is a demonstration, not an automatic timing measurement.

## Existing consumers

Stepper motor probes and PanTltStepper now call the shared GPIO object. Their motion planning and pulse timing algorithms are unchanged. The stepper_motor target publicly links hardware_gpio, and gpio_probe and pan_tlt_probe link it directly, making platform dependencies transitively available to consumers. The old global no-op GPIO functions and PI_INPUT/PI_OUTPUT aliases were removed from hardware.h; callers use Gpio and GpioMode.
