# PWM у GPIO API

Документ описує поточну реалізацію `Gpio` для Raspberry Pi 4, Raspberry Pi 5 та desktop, налаштування ОС і межі програмних перевірок. Усі номери пінів тут — GPIO/BCM, а не номери контактів 40-pin роз’єму.

## Що визначають параметри

PWM періодично перемикає вихід між LOW і HIGH:

- `frequency` — кількість періодів за секунду, Гц.
- `range` — ціла шкала для duty, а не час чи апаратний лічильник.
- `duty` — частина цієї шкали, протягом якої вихід HIGH.
- `enabled` — чи потрібно генерувати заданий сигнал.

Формули:

```text
period = 1 / frequency
HIGH time = period × duty / range
LOW time  = period − HIGH time
```

Наприклад, frequency=1000, range=100, duty=25 означає період 1 мс: приблизно 250 мкс HIGH і 750 мкс LOW. Range=50, duty=50 означає постійний HIGH; повторюваних фронтів немає. Range=100, duty=50 і range=200, duty=100 задають однакові 50%, хоча крок шкали різний.

Межі спільного API для всіх реалізацій:

| Параметр | Допустимі значення | Початкове значення |
|---|---|---|
| range | 1…40000 | 100 |
| duty | 0…range | 0 |
| frequency | 1…10000 Гц, ціле число | 1000 |
| enabled | false / true | false |

Ці межі є контрактом обгортки. Апаратні контролери можуть мати ширші можливості, але поточний API їх не відкриває. Частота 0 не означає OFF: використовуйте `setEnabled(pin, false)`.

Зміна RANGE зберігає числове DUTY. Наприклад, range=100, duty=25 після setRange(50) дає 50%. Зменшення range нижче поточного duty відхиляється; спочатку зменшіть duty.

## Вибір механізму

```cpp
gpio.setMode(pin, GpioMode::output);       // звичайний GPIO та поточний PWM
gpio.setMode(pin, GpioMode::hardwarePwm);  // виділений апаратний PWM
```

Режим обирається окремо для кожного піна. Наявні виклики зі звичайним OUTPUT зберігають поведінку.

| Платформа | `output` + PWM | `hardwarePwm` |
|---|---|---|
| RPI4 | pigpio `gpioPWM`, планування з DMA | pigpio `gpioHardwarePWM` |
| RPI5 | lgpio `lgTxPwm`, програмні таймінги | PWM0 контролера RP1 через драйвер Linux/sysfs |
| Desktop | стан у пам’яті без генерації фронтів | емуляція контракту з таблицею каналів RPI4 |

Звичайний PWM доступний на дозволених вільних виходах GPIO0…27. Апаратний — тільки на відповідних пінах і каналах. Код не переходить автоматично на програмний PWM, якщо апаратний недоступний.

`hardwarePwmChannel(pin)` повертає номер апаратного каналу або `NOT_SUPPORTED`; цей запит можливостей не захоплює ресурс і не підтверджує, що overlay чи дозволи вже налаштовані.

## Піни та канали

| GPIO | Фізичний контакт | Канал RPI4 | Канал RPI5 |
|---|---:|---:|---:|
| 12 | 32 | 0 | 0 |
| 13 | 33 | 1 | 1 |
| 14 | 8 | немає | 2 |
| 15 | 10 | немає | 3 |
| 18 | 12 | 0 | 2 |
| 19 | 35 | 1 | 3 |

Особливо важливо: GPIO18/19 — канали 0/1 на Pi 4 та 2/3 на Pi 5. Номер каналу є локальним для PWM-контролера.

На Pi 4 GPIO12 і GPIO18 спільно використовують канал 0, GPIO13 і GPIO19 — канал 1. На Pi 5 такі пари — GPIO14/18 і GPIO15/19. Обгортка дозволяє одному піну володіти каналом: спроба вибрати його другий пін поверне `CHANNEL_BUSY`, навіть коли PWM логічно OFF. Це запобігає зміні сигналу вже вибраного піна через його альтернативний вихід.

Ця перевірка діє всередині спільного об’єкта `Gpio`. Вона не є міжпроцесним блокуванням. Для Pi 5 додатково перевіряється результат sysfs export; уже експортований канал не переймається. Іншим процесам не слід паралельно керувати тими самими ресурсами.

GPIO14/15 часто використовуються UART; GPIO18/19 можуть використовуватися іншими периферійними функціями. Програміст обирає вільні піни й узгоджує Device Tree. Не маршрутизуйте один канал одразу на кілька пінів, якщо не потрібен той самий сигнал на всіх цих виходах.

Таблиця заснована на [pigpio API](https://github.com/joan2937/pigpio/blob/master/pigpio.h) та [RP1 Peripherals, таблиця 4](https://datasheets.raspberrypi.com/rp1/rp1-peripherals.pdf).

## Послідовність роботи та помилки

1. Викликати `initialize()`.
2. Вибрати `output` або `hardwarePwm` через `setMode()`.
3. Встановити range, duty та frequency.
4. Увімкнути через `setEnabled(pin, true)`.
5. Змінювати налаштування або вимкнути через `setEnabled(pin, false)`.
6. Завершити роботу через `terminate()`.

Успіх — 0, помилка — від’ємне число. Виняток: звичайний `read()` повертає рівень 0/1, а `hardwarePwmChannel()` — номер каналу. Перевіряйте результат кожної операції.

`getPwmSettings()` повертає останні прийняті налаштування, не фізично виміряний сигнал. OFF зберігає RANGE, DUTY і частоту, тому наступний ON відновлює заданий сигнал.

У режимі `hardwarePwm` `read()` і `write()` повертають `WRONG_MODE`, навіть після OFF. Це навмисне: пін залишається призначеним контролеру PWM. Для звичайного цифрового запису потрібен успішний перехід у OUTPUT. На Pi 5 такий перехід може бути неможливий, доки overlay резервує пін для драйвера PWM; обгортка не вивантажує overlays і не перепризначає pinmux через /dev/mem.

У режимі OUTPUT цифровий `write()` під час увімкненого PWM повертає `PWM_ACTIVE`; після OFF знову доступний.

| Помилка | Значення |
|---|---|
| `INVALID_ARGUMENT` (-10000) | пін, режим або параметри поза дозволеними межами |
| `NOT_INITIALIZED` (-10001) | потрібна ініціалізація |
| `WRONG_MODE` (-10002) | операція не відповідає режиму чи пін не налаштований |
| `PWM_ACTIVE` (-10003) | спроба цифрового запису під час звичайного PWM |
| `CHIP_NOT_FOUND` (-10004) | не знайдено GPIO-контролер |
| `NOT_SUPPORTED` (-10005) | пін не підтримує апаратний PWM або канал відсутній |
| `CHANNEL_BUSY` (-10006) | канал уже зайнятий або експортований |
| `PWM_NOT_CONFIGURED` (-10007) | не знайдено відповідний RP1 PWM0 із потрібною маршрутизацією |

Нативні помилки pigpio/lgpio передаються без перетворення. Sysfs повертає `-errno`, зокрема `-EACCES`, `-ENOENT`, `-EINVAL`, `-EIO`; контекст реалізації визначає значення коду.

Некоректні аргументи відхиляються до застосування. Послідовність записів у драйвер не є транзакцією: після I/O-помилки фізичний стан може відрізнятися від останніх прийнятих налаштувань. Sysfs-реалізація намагається повернути duty до нуля, але помилка доступу не дозволяє гарантувати результат. Обробіть помилку, повторіть вимкнення або виконайте cleanup; не продовжуйте мовчки.

## Приклад апаратного PWM

Приклад для вільного GPIO12; для Pi 5 спочатку потрібне налаштування ОС нижче. Це фрагмент застосунку, а не зміна gpio_probe.

```cpp
#include "hardware/gpio/gpio.h"
#include <chrono>
#include <cstdio>
#include <thread>

constexpr unsigned PWM_PIN = 12;
constexpr unsigned PWM_RANGE = 100;
constexpr unsigned PWM_DUTY = 25;
constexpr unsigned PWM_FREQUENCY = 1000;
constexpr char ON_MAIN[] = "on main(): ";

int main() {
    auto& gpio = Gpio::instance();
    int result = gpio.initialize();
    if (result >= 0) { result = gpio.setMode(PWM_PIN, GpioMode::hardwarePwm); }
    if (result >= 0) { result = gpio.setRange(PWM_PIN, PWM_RANGE); }
    if (result >= 0) { result = gpio.setDuty(PWM_PIN, PWM_DUTY); }
    if (result >= 0) { result = gpio.setFrequency(PWM_PIN, PWM_FREQUENCY); }
    if (result >= 0) { result = gpio.setEnabled(PWM_PIN, true); }
    if (result >= 0) {
        std::this_thread::sleep_for(std::chrono::seconds(5));
        result = gpio.setEnabled(PWM_PIN, false);
    }
    const int closed = gpio.terminate();
    if (result >= 0) { result = closed; }
    if (result < 0) {
        std::fprintf(stderr, "%sPWM failed: %d\n", ON_MAIN, result);
        return 1;
    }
    return 0;
}
```

Ціль застосунку має лінкуватися з `hardware_gpio`.

## RPI4: доступ через pigpio

Для апаратного PWM використовується вже наявна залежність pigpio. Окремий Linux PWM overlay для цієї реалізації не потрібний; не призначайте той самий контролер одночасно kernel PWM та pigpio. Вимоги до привілеїв залишаються такими самими, як для прямого gpioInitialise у вашій системі.

Обгортка перетворює частку DUTY/RANGE на шкалу 1000000 бібліотеки. Це шкала аргументу, а не обіцянка мільйона фізичних кроків точності. У звичайному GPIO PWM шкала pigpio встановлюється у 40000.

Апаратний виклик вимагає основного clock pigpio PCM; це стандартне налаштування бібліотеки. Виклик gpioHardwarePWM скасовує передавання хвиль gpioWaveTxSend/gpioWaveChain. Не поєднуйте ці механізми без окремого узгодження ресурсів. [Обмеження pigpio](https://github.com/joan2937/pigpio/blob/master/pigpio.h).

## RPI5: драйвер, overlay та доступ

lgpio використовується для звичайних GPIO; апаратний PWM використовує окремий драйвер ядра. `initialize()` все одно відкриває GPIO-контролер RP1, тому потрібний доступ і до gpiochip, і до PWM sysfs.

Для двох каналів на GPIO12/13 типовий запис у `/boot/firmware/config.txt`:

```ini
dtoverlay=pwm-2chan,pin=12,func=4,pin2=13,func2=4
```

Після зміни конфігурації перезавантажте плату. Для стандартної пари GPIO18/19 типовий варіант — `dtoverlay=pwm-2chan`; у RP1 це канали 2/3. Точну підтримку й параметри перевіряйте на самій платі командою `dtoverlay -h pwm-2chan` та у `/boot/firmware/overlays/README`. Імена й адаптація overlays залежать від встановленого kernel/firmware; одна назва Bookworm або Trixie не визначає їх версію.

Цей двоканальний overlay не означає автоматичне підключення всіх чотирьох каналів RP1. Для чотирьох виходів потрібна відповідна конфігурація pinctrl у власному overlay, наприклад GPIO12, GPIO13, GPIO18, GPIO19 із функцією `pwm0`, прив’язана до `rp1_pwm0`. API підтримує всі чотири канали, але ОС повинна маршрутизувати кожний вибраний пін. [Overlays Raspberry Pi](https://github.com/raspberrypi/linux/blob/rpi-6.12.y/arch/arm/boot/dts/overlays/README), [RP1 Device Tree](https://github.com/raspberrypi/linux/blob/rpi-6.12.y/arch/arm64/boot/dts/broadcom/rp1.dtsi).

Обгортка шукає контролер за compatible `raspberrypi,rp1-pwm` і вузлом `pwm@98000`, а не за номером pwmchip. Перевіряє pinctrl-0 і відповідні phandle в активному Device Tree. Підтримуються прямі pinctrl-групи з `pins`/`function` та legacy `brcm,pins`/`brcm,function`. Вкладені довільні групи не розбираються; для них буде PWM_NOT_CONFIGURED. Контролер `pwm@9c000` не використовується.

Потрібні права читання Device Tree й права запису до `export`, `unexport` та атрибутів експортованого каналу. Вони залежать від правил udev у конкретній ОС. Наявність групи gpio сама по собі не доводить доступ до всіх PWM-файлів. Обгортка не змінює права та не виконує sudo. Після export вона очікує появи й дозволів enable до приблизно 500 мс.

Діагностика без генерації сигналу:

```sh
uname -r
dtoverlay -h pwm-2chan
ls -l /sys/class/pwm/
```

У знайденому `pwmchipN` перевірте `npwm` і посилання `device/of_node`. Не припускайте, що `pwmchip0` або `pwmchip2` завжди означає той самий контролер. Не експортуйте канал вручну перед використанням API: API розцінить його як зайнятий. Якщо процес аварійно завершився й залишив export, звільнення такого каналу — окрема дія адміністратора після перевірки, що він більше ніким не використовується.

## OFF, завершення та точність

В апаратному режимі OFF означає нульовий duty при активному контролері. Так зберігається LOW і залишається можливість відновити налаштування наступним ON. `enabled=false` у PwmSettings — логічне OFF нашого API; на Pi 5 sysfs enable при цьому дорівнює 1.

`terminate()` та зміна режиму звільняють ресурс. На Pi 5 канал вимикається і unexport-иться. Після звільнення гарантія LOW більше не діє: загальний Linux PWM API не гарантує рівень вимкненого контролера. Для утримання LOW залишайте ресурс відкритим і використовуйте OFF. Після SIGKILL чи втрати живлення код cleanup не виконується. [Семантика Linux PWM](https://www.kernel.org/doc/html/latest/driver-api/pwm.html).

Період у sysfs обчислюється як ціла кількість наносекунд `1000000000 / frequency`, а duty — як `period * duty / range`. Драйвер і тактова частота контролера додають власне округлення. Зміна частоти спочатку задає нульовий duty, щоб старе HIGH-time не перевищило новий період. Можлива коротка пауза LOW; безперервне чи синхронне перемикання всіх каналів не гарантується.

Апаратний PWM зменшує залежність фронтів від планувальника Linux. Проте момент старту, зупинки та зміни параметрів з userspace не є операціями реального часу. Це генератор періодичного сигналу, а не генератор точно N STEP-імпульсів: для точного переміщення двигуна потрібен окремий механізм підрахунку/планування.

## Автоматичні тести

Жоден новий тест апаратного режиму не потребує плати, перемичок або вимірювача:

- `gpio_contract_test` завжди використовує desktop: перевіряє режими, параметри, таблиці каналів, конфлікти альтернативних пінів, збереження налаштувань після OFF і заборону цифрових операцій у hardwarePwm.
- `pwm_sysfs_test` перевіряє послідовність записів, перерахунок періоду/duty, 0% і 100%, чужий export, помилки та cleanup через тестовий транспорт. Окремі тести читають штучний Device Tree у тимчасовій директорії: інший номер pwmchip, phandle, pin/function і виключення іншого контролера.
- Існуючий `gpio_test` залишається перевіркою цифрового OUTPUT на пінax, заданих у hardware.h. На Raspberry Pi він використовує реальні піни; нові тести вище — ні.

```sh
cmake --build base/cmake-build-release --target gpio_contract_test pwm_sysfs_test
ctest --test-dir base/cmake-build-release -R '^(gpio_contract_test|pwm_sysfs_test)$' --output-on-failure
```

Заглушка не симулює PWM-фронтів і не є підтвердженням фізичної частоти чи duty. Перевірка заголовків компілятором також не замінює запуск на RPI4/RPI5. Оригінальний `gpio/_probes/gpio_probe.cpp` залишено цифровим пробником із блиманням; цей документ не змінює його сценарій.
