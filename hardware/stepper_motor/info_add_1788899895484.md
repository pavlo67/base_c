# Cruise before timed braking

Timed accelerated moves can now contain Acceleration, Cruise, Deceleration and the separately reserved terminal pulse. This supersedes the statement in `info.md` that clocked moves have no separate cruise section. The zero-timer ideal construction and its triangular/trapezoidal choice are unchanged.

`getCruiseAndBraking(speedDegPerSec, finalSpeedDegPerSec, remainingPulses, timer, options, algorithm, startedAt=0, livePwm=false)` returns evaluated optional cruise and braking sections. Inputs use the existing validated motor options, signed reached/target speeds and a remaining pulse budget excluding the terminal pulse. It first evaluates braking without a completion minimum using the selected timer/PWM model. Any surplus displacement is assigned to cruise at the reached speed. Cruise tick overshoot and the shifted braking start are evaluated together; the cruise budget is reduced when their predicted combined count exceeds the remaining displacement. With no available surplus, only braking is returned. Any residual shortfall still uses the existing braking completion minimum.

Live execution replaces the planned cruise/braking tail when acceleration completes, using its reached speed and observed pulse count. Prediction uses the largest spacing between external calls observed so far on a synthetic timer grid. This avoids assuming that one unusually short tick represents subsequent execution, but cannot predict future scheduler delays or physical PWM edges. After cruise, braking is rebuilt with the actual remaining pulse budget. Completed-section metadata is retained across vector insertion; planned cruise is replaced rather than duplicated.

Cruise uses `stopAfterPulses_` to stop on the first call reaching its displacement threshold, independent of interval-law progress. Its `pairedTargetPulses_` holds the combined remaining cruise/braking budget. On acceleration this field still holds the entire pre-terminal move budget. These planning fields survive reset. `cruiseFrequency_` preserves the reached integer-Hz live PWM command across reset and avoids losing one Hz through floating-point speed-to-frequency conversion. Existing speed and acceleration limits still apply.

For deterministic desktop execution of signed 33-degree moves with a 5-ms timer, the regression observes four cruise pulses and preserves all 147 total pulses. Cruise plus main braking takes about 0.370 seconds versus 0.460 seconds for the preceding no-cruise braking model; both exclude the unchanged terminal interval. These are runtime-model comparisons, not Raspberry Pi waveform or mechanical measurements. Depending on the timer model and available displacement, a clocked plan may have no cruise while its live execution has one.

GTest/CTest coverage checks both directions, unchanged 33-degree ideal triangles, simulated cruise and shorter completion for 180-degree moves, no cruise when braking consumes the remaining budget, preservation of reached live frequency and total displacement, and replacement of planned cruise under alternating 4/6-ms calls. Previously existing finite terminal speed, acceleration bounds, timer replay and GPIO cleanup checks remain applicable. Future unobserved timing delays can still produce target overshoot or a slow completion remainder; this change does not turn free-running PWM into an exact physical pulse counter.
